## Datos de prueba necesarios
- Usuario seed de dev (`qa@probo.dev`, contraseña por secreto) y usuario de smoke de prod. Se crean con el seed en cada deploy (seed.ts); no hay que crear ni limpiar datos de negocio.
- Email inexistente con formato válido, generado por test (ej. `noexiste-<uuid>@probo.dev`).
- Variantes del email seed: mayúsculas, espacios alrededor (dependen de la pregunta 2).
- Contraseña incorrecta, contraseña con mayúsculas cambiadas, contraseña vacía.
- Emails inválidos: sin `@`, sin dominio, con espacios internos, largo > máximo (depende de la pregunta 4).
- Tokens: válido, alterado (firma rota), mal formado, expirado (depende del riesgo 2).
- Bodies inválidos para la API: `{}`, sin `password`, sin `email`, tipos incorrectos, JSON mal formado.

## Notas para el diseño de casos
- **Particiones de equivalencia:** email (existente / inexistente válido / formato inválido / vacío / mayúsculas o espacios) × contraseña (correcta / incorrecta / vacía).
- **Tabla de decisión:** email vacío/inválido/válido × contraseña vacía/con valor → resultado (validación de front sin request / 401 / 200). Útil para separar qué se prueba en UI y qué en API.
- **Valores límite:** expiración en API (`exp` justo antes y justo después); largo máximo del email si se define.
- **Negativos API:** 400 con `VALIDATION_ERROR` y `details`; 401 con cuerpo **idéntico** para email inexistente y contraseña incorrecta; la respuesta nunca incluye `passwordHash`.
- **UI:** en CA4/CA5 verificar con un listener de red que no sale ningún request a `/api/auth/login`.
- **BDD (HU candidata):** `Esquema del escenario` para credenciales inválidas y para validaciones de formulario; los steps reutilizan un `LoginFlow` de `tests/flows/`.
- **@smoke:** login OK con el usuario de smoke en prod, sin adjuntar trace (riesgo 1).
