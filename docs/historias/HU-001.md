# HU-001: Iniciar sesión
**Épica:** E1 Acceso · **Prioridad:** alta · **Estimación:** 3 pts

**Como** QA usuario de Probo
**Quiero** iniciar sesión con mi email y contraseña
**Para** acceder a mis historias y casos de prueba de forma privada

## Criterios de aceptación
- [ ] **CA1** Dado un usuario registrado, cuando ingresa email y contraseña correctos, entonces es redirigido a `/historias` y ve el header de la app.
- [ ] **CA2** Dado un usuario registrado, cuando ingresa una contraseña incorrecta, entonces ve "Email o contraseña incorrectos", sigue en `/login`, el email se conserva y la contraseña se limpia.
- [ ] **CA3** Dado un email que no existe, cuando intenta ingresar, entonces ve exactamente el mismo mensaje "Email o contraseña incorrectos" (no se revela si el email existe).
- [ ] **CA4** Dado el formulario, cuando envía con email o contraseña vacíos, entonces ve "Campo obligatorio" debajo de cada campo vacío y no se envía ningún request a `/api/auth/login`.
- [ ] **CA5** Dado el formulario, cuando ingresa un email sin formato `x@dominio.tld` o de más de 254 caracteres, entonces ve "Email inválido" debajo del campo y no se llama a la API.
- [ ] **CA6** Dado un usuario con sesión iniciada, cuando recarga la página, entonces sigue en la misma pantalla sin pasar por el login (el front valida el token con `GET /api/auth/me`).
- [ ] **CA7** Dada una sesión iniciada, cuando se cumplen **8 horas absolutas** desde el login, entonces el siguiente request responde 401 y el front lo lleva a `/login` con "Tu sesión expiró. Iniciá sesión de nuevo."
- [ ] **CA8** Dado un email con mayúsculas o espacios al inicio/final (ej. `" QA@Probo.dev "`), cuando ingresa con la contraseña correcta, entonces inicia sesión (el email se normaliza con `trim` + minúsculas).
- [ ] **CA9** Dada una contraseña, cuando tiene espacios, entonces se respetan tal cual (no se aplica `trim`); solo `""` cuenta como vacía.
- [ ] **CA10** Dado que la API no responde o devuelve un error 5xx, cuando intenta ingresar, entonces ve "No se pudo conectar. Intentá de nuevo." y el email se conserva.
- [ ] **CA11** Dado el formulario enviado, cuando el request está en curso, entonces el botón queda deshabilitado con el texto "Ingresando…" (un doble clic no genera dos requests).
- [ ] **CA12** Dado un usuario con sesión activa, cuando entra a `/login`, entonces es redirigido a `/historias`.

### API
- [ ] `POST /api/auth/login` con credenciales válidas responde **200** `{ token, user: { id, email } }`.
- [ ] Con credenciales inválidas (contraseña incorrecta o email inexistente) responde **401** `{ "error": "INVALID_CREDENTIALS" }`, idéntico en ambos casos.
- [ ] Con body incompleto, email mal formado o de más de 254 caracteres responde **400** `{ "error": "VALIDATION_ERROR", "details": [{ field, message }] }`.
- [ ] `GET /api/auth/me` con token válido responde **200** `{ id, email }`; sin token, con token inválido, alterado o expirado responde **401** `UNAUTHORIZED`.
- [ ] El token expira a las 8 horas del login (`exp` del JWT).

## Notas
- **Decisión:** no hay registro en el MVP; los usuarios se crean por seed (uno de tests en dev, uno de smoke en prod).
- **Decisión:** contraseña guardada con hash **bcrypt**, nunca en texto plano.
- **Decisión:** el token se guarda en `localStorage` (simple para el MVP; cookie httpOnly queda como mejora de seguridad).
- **Decisión:** mientras no exista HU-004, `/historias` muestra un placeholder con el header; CA1 verifica la URL y el header, no el listado.
- **Testabilidad:** para CA7 el TTL del token es configurable por variable (`JWT_TTL`, por defecto 8 h) y los tests controlan el reloj del navegador o usan un TTL corto en un test de API dedicado.
- **Seguridad de evidencias:** los tests de login no deben dejar contraseñas ni tokens en traces, screenshots o adjuntos de Allure (el reporte es público).
- **Fuera:** recuperar contraseña, bloqueo por intentos fallidos.
- **Candidata a BDD.**
